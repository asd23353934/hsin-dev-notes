# 代理開發下的人工驗收

> 當專案的實作由 AI 代理鏈接單完成（orchestrator 分派：讀需求產設計 → dev → QA → SRE → 出 MR），
> 人只負責**派工前審單**與**派工後驗收**時的工作法。
> 收的是「會讓結論錯掉」的判準，不是某個專案的 SOP；專案專屬的站點、角色、單號留在該專案的 `CLAUDE.md`。
> 最後更新：2026-10-20

---

## 1. 人補的是哪四個縫

代理鏈裡的 QA / SRE 已經跑過 smoke / unit / api / e2e，**人不要重跑那些**——重跑只會拿到同樣的綠燈。
機器驗「有沒有做」，人驗「做的是不是那件事」。缺口固定是這四個：

1. **需求 ↔ 設計**：產設計那一步漏掉的條目
2. **設計 ↔ 實作**：設計裡列的 endpoint / 欄位沒做完
3. **實作 ↔ 規範**：專案既有慣例被違反（一檔多職責、死碼、hardcode）
4. **業務語意**：跑得動、格式也對，但業務上是錯的

第 4 條機器永遠驗不到，**人的時間優先花在它上面**；前三條能 lint 就 lint，不要用肉眼做機器的事。

⚠️ **代理讀不到的地方就別放關鍵約束**。若「產設計」那一步只讀需求正文、不讀留言，寫在留言的補充施工時就不保證吃得到。
判準：這句話漏掉，代理會不會做出**看起來對、實際錯**的東西？會 → 必須進正文，或等實作出來後走修正回合，光留言不夠。

## 2. 驗收時這些都不能當事實

| 不能信 | 為什麼 |
|---|---|
| 本機 clone 的源碼 / grep 命中 | clone 會 stale、key 不全；命中的可能是別的頁或多 view 頁 |
| 截圖裡的控件狀態 | 未選中的按鈕在小圖裡看起來就像停用 |
| 系統吐的 label / reason / status | 可能是「查無資料」的 fallback，先追它從哪個分支來，再驗底層事實 |
| 「同機制推斷」 | 同類功能不代表同實作，逐項各別實測過才寫 |
| 自動化平台自述的「環境已隔離」 | 服務隔離常常不等於資料隔離，自己連進去查一次 |
| 需求單上對現況的描述 | 那是開單者的認知，不是現況，要實機確認問題真的存在 |

🔴 **UI 鎖住 ≠ 後端擋得住**。欄位改唯讀 / `disabled` / 整格藏起來，不代表 API 拒收。
只走畫面判 PASS 是這類單最貴的漏法——踩過「第一輪畫面 PASS、第二輪直打 API 才看到值照樣寫得進去」，本來兩輪的事變三輪。

所以驗「這一頁能設定什麼」的單，**第一輪就把可寫欄位列出來**逐一跑：畫面擋住的直接送值試（收了＝只有畫面在擋）、
每個可寫欄位跑邊界值（`0` / 負數 / 遠超合理範圍 / 超精度小數 / 空字串）、錯誤訊息不得是 SQLSTATE 或框架 binding 的 struct 名。

同時：**預設走真實 UI 點擊輸入，不要用 API 代操作**——真實操作會一併驗到防呆與驗證訊息，API 整層繞過去。
兩者不衝突：UI 驗「功能對不對」，API 驗「把關在不在」。

## 3. 對共用環境寫入前，先分可逆與不可逆

動手前把要做的事分兩類，這比「小心一點」有用得多：

- **改得回去**：改既有列的值 → 寫回原值就還原
- **改不回去**：異動紀錄（每次寫入都落一筆）、該列的 `updated_by` 會變成你、新建的單據多半只能作廢不能刪

推論是反直覺的那個方向：**邊界值要一輪掃完**（一次帶齊各種值再還原），不要分幾次來回試——
值改得回去，紀錄改不回去。真正該收斂力氣的是「建假資料」那類，不是改既有列。

**用誰的資料，跟寫不寫一樣要先想。** 共用環境裡每個人都在測，借別人的資料會雙向污染：
你改設定，別人的測試跟著變；別人改了，你驗到一半的數字跟著變。判準是這筆資料**能不能有自己一份**：

| 類型 | 例子 | 做法 |
|---|---|---|
| 能有自己一份 | 帳號、客戶、品項、耗材、場地、班別、角色、方案、標籤 | 建一份、名稱加自己的前綴，往後固定用這份 |
| 建得出來，但一啟用就影響同範圍的所有人 | 簽核規則、折扣、行銷活動 | 建成停用或草稿，只在要驗的那段打開，驗完關回 |
| 只有一份 | 全域設定、各據點的設定 | 改了立刻改回、記 log |

這跟上面「收斂建假資料」不衝突：收斂的是每輪新造的樣本；固定一份、反覆復用的主檔，反而讓你不必再借、也不必再造。

- ⚠️ **「用自己的帳號」要連「指派給誰」一起算**。只管登入身分、不管流程裡指派的負責人，業績和負責人照樣記到別人身上——
  踩過：登入一律是自己的，被指派的人卻大多是 seed 帳號（約 45 次對 6 次）。
- ⚠️ **隔離得了與否，看那條規則能用什麼篩**。只能按角色、據點篩、不能按帳號篩的規則，做不到「只給我用」，
  只能靠平時停用；能綁到自己品項的（例如「買某品項才觸發」），啟用了也只影響自己。

寫入外部系統（共用 DB、issue tracker、CI）完成後立刻 append 到一份 log：做了什麼、在哪、有沒有還原。純讀取不記。

## 4. 知識庫要有失效機制

多數知識庫只有**寫入**機制（踩到就記），沒有**失效**機制——沒有任何東西會回頭質疑舊條目還對不對。
於是規則慢慢爛掉，而**錯的規則比沒有規則危險**：它每次都被載入，人和 AI 都會穩定地照錯的做，而且講得有把握。

唯一可行的機制是把它掛在「使用」上：**照著某條規則做、卻發現與現況不符時，當場查證並改掉那條**，
不要繞過去、也不要只在對話裡講一句就算。曾經一天內抓到三條，全是同一個型態：**曾經對、環境變了、沒人回頭改**。

配套的分層，判準是「**三個月後還對不對**」：

| 層 | 特徵 | 放哪 |
|---|---|---|
| 架構 / 流程 | 跨 session 穩定、是一張連通圖 | 專案 `CLAUDE.md` |
| 可複用結論 / 教訓 | 一檔一事實、按相關性召回 | memory |
| 當前任務狀態 / 交接 | 會過時 | `HANDOFF.md` |
| 一次性中間產物 | 用完即棄 | 不進知識庫 |

⚠️ **守門型規則不能放 memory**。memory 是按相關性召回的，等對話「聊到」時往往已經動手了；
「什麼時候不准自己動」這類要一直在，得放每次都載入的那層。

## 5. 走查腳本當程式碼經營，不是拋棄式腳本

- **共用開場**：登入 / session / API helper 封裝成一支，把踩過的雷寫死在裡面——
  等狀態轉移不盲等秒數、失敗就 throw 不吞錯、跨 token 驗權限的 fetch 一律 `cache: 'no-store'`
  （最後這條漏掉會拿到前一個「有權請求」的快取，回**假的 200**，足以誤報成高危洞）。每支重寫登入 ＝ 每支各踩一次。
- **寫 selector 之前先 probe**：印出這頁可點的東西（文字 / testid / 可見可用 / 在哪個容器）。
  猜 selector 是走查最大的往返來源；浮層元件常 `appendTo` body，靠容器才分得出是哪一顆。
- **selector 沒命中 ≠ 功能壞掉**：不同框架 DOM 不同，通用 selector 假陰性很常見；
  元件初次 render 可能寬 0，**resize 後才出現 ⇒ 那是 first-render layout bug，不是功能缺**。
- **封存目錄不參與收集**：舊腳本移進 `_archive/` 並在 test runner 設 ignore。
  一支語法壞掉的檔就能讓整個收集失敗跑出 0 tests；而且舊腳本多半含寫入，本來也不該被整批跑到。

## 6. 探索的任務從哪來：Whittaker 的 23 種 tour

只從「撞到可疑的地方」出發，一輪探索跑下來往往全是同一種形狀（踩過：五個情境全是「照正常動線走一遍」），
而當天最大的發現卻是另一種形狀、偶然撞到的。**把 tour 當 charter 的來源，刻意換形狀。**

出處：James Whittaker《Exploratory Software Testing》（2009）第 4 章，簡中譯本《探索式軟件測試》「全局探索式測試法」。
把軟體比成一座城市、測試者當觀光客，依去哪一區分 6 區 23 種。名稱照簡中譯本（「破壞者」原文就沒有「測試法」三字）。

| 區 | 測試法 | 原文 | 做法 |
|---|---|---|---|
| 商業區 | 指南測試法 | Guidebook | 照使用手冊／說明一步步做，看實際行為跟文件對不對得上 |
| | 賣點測試法 | Money | 測拿來賣、demo 會演的功能；變體「質疑測試法」（Skeptical Customer）是 demo 中途像挑剔的客戶一樣一直問「那如果…」 |
| | 地標測試法 | Landmark | 挑幾個關鍵功能當地標，排好先後順序在地標間走，再換順序走 |
| | 極限測試法 | Intellectual | 問軟體最難的問題：最大值、最複雜的組合、把它推到設計極限 |
| | 快遞測試法 | FedEx | 跟著一筆資料走，找出每個碰到它的功能（輸入→儲存→計算→顯示） |
| | 深夜測試法 | After-Hours | 使用者不在時跑的背景工作：備份、排程、批次；變體 Morning-Commute 測啟動流程 |
| | 遍歷測試法 | Garbage Collector's | 選一類目標（所有選單／錯誤訊息／對話框），用最短路徑逐一點過，廣而不深 |
| 歷史區 | 惡鄰測試法 | Bad-Neighborhood | 缺陷會群聚，之前 bug 多的地方反覆測 |
| | 博物館測試法 | Museum | 老程式碼：被改過的舊碼，或沒改、直接搬進新環境跑的 |
| | 上一版測試法 | Prior Version | 拿上一版的情境在新版重跑，看哪些跑不動、變了、被拿掉 |
| 娛樂區 | 配角測試法 | Supporting Actor | 緊鄰主功能、看得到卻容易被忽略的功能 |
| | 深巷測試法 | Back Alley | 最少人用、最不吸引人的功能 |
| | 通宵測試法 | All-Nighter | 開著一直用、不關不重整，看長時間累積下來會不會出事 |
| 旅遊區 | 收藏家測試法 | Collector's | 想辦法讓軟體產出每一種可能的輸出，收集越多越好 |
| | 長路徑測試法 | Lonely Businessman | 繞最遠的路去埋最深的那個畫面 |
| | 超模測試法 | Supermodel | 只看表面：版面、樣式、文字，不管功能 |
| | 測一送一測試法 | TOGOF | 同時開多個拷貝操作（Web 上＝多分頁、多人同時改同一筆） |
| | 蘇格蘭酒吧測試法 | Scottish Pub | 找要有內行人帶路才找得到的角落 |
| 旅館區 | 取消測試法 | Rained-Out | 啟動操作再中途停掉；或取消前先改狀態、或不取消直接開第二個操作 |
| | 懶漢測試法 | Couch Potato | 盡量少做事：全部接受預設值、能空就空 |
| 破舊區 | 破壞者 | Saboteur | 拿掉或限制它運作要用的資源（檔案、網路、記憶體這類）；Web 上大概是斷網、API 失敗或逾時、操作途中 token 過期 |
| | 反叛測試法 | Antisocial | 做軟體不希望你做的事，三個子型：逆向（Opposite，輸入最不可能的資料）、歹徒（Crime Spree，輸入不該出現的資料）、錯序（Wrong Turn，用錯的順序做事） |
| | 強迫症測試法 | Obsessive-Compulsive | 同一件事反覆做：連點、重送、同樣資料再輸入一次 |

⚠️ **自己起的簡稱別掛錯原書的名字**。踩過：把「邊界值、順序顛倒、用別人的身分操作、中途離開」整格標成 Saboteur——
那其實是反叛的三個子型加上取消；原書的破壞者專指**拿掉資源**，那一類根本不在清單上。
名字掛錯的代價不是用詞不精確，是**以為某一類跑過了，其實它不在清單上**。

🔴 破舊區與取消測試法多半會寫入。在共用環境照 §3 先分可逆與不可逆，而且**預期會被擋也要先想「萬一成功怎麼收」**：
範圍壓到最小、還原的路事前確認存在、成功就立刻收、不要接著往下探。
